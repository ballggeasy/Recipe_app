## 2. Current Architecture

```
Flutter app ──HTTP/JSON──▶ NestJS controllers ─▶ services ─▶ TypeORM repositories ─▶ SQLite file
 provider ▶ service ▶ ApiClient                  (JwtAuthGuard per route)
```

* Controllers are already thin; business rules live in services. This matches the target layering — **no restructuring needed**.
* Authorization is ownership checks inside services (`uploaderId`, `userId`). Consistent for recipes, comments, meal plan, folders; missing for `reviews/:id/report`.
* One global `ValidationPipe`; errors are Nest defaults (no shared error shape, no request id).
* Persistence: `synchronize: true` against SQLite — schema is auto-altered on boot, no migrations.

## 3. Problems Found

### Security
| # | Finding | Evidence |
|---|---------|----------|
| S1 | **Unauthenticated password reset = account takeover.** Anyone can `POST /auth/reset-password {email, newPassword}` for any account; `GET /auth/exists/:email` confirms which emails are registered. | `auth.controller.ts:42-53`, `forgot_password_screen.dart` |
| S2 | **Hard-coded fallback JWT secret** (`'change-this-secret-in-production'`, also the value in `.env.example`). If `JWT_SECRET` is missing the server boots and tokens are forgeable. | `auth.module.ts:14`, `jwt.strategy.ts:17` |
| S3 | User enumeration: login returns 404 for unknown email vs 401 for wrong password. | `auth.service.ts:60-67` |
| S4 | Vulnerable dependencies: `multer@1` (high, DoS), `@nestjs/platform-express`/`body-parser`/`qs`, `lodash` via `@nestjs/config`, `uuid`; `tar`/`node-gyp` via `sqlite3` (build-time only). | `npm audit --omit=dev` |
| S5 | `enableCors()` allows every origin; no security headers; no rate limiting on login/register/reset (bcrypt is CPU-bound → cheap DoS and brute force). | `main.ts` |
| S6 | `/metrics` is public on the same port as the API (exposes process/route data). | `metrics.controller.ts`, `docker-compose.yml` |
| S7 | Any user can set `isRecommended` on their own recipe (mass-assignment via `CreateRecipeDto`/`UpdateRecipeDto`). | `create-recipe.dto.ts:124` |
| S8 | JWT is valid 7 days and survives password change; access token stored in `SharedPreferences` (plaintext / web localStorage). | `auth.module.ts`, `api_client.dart` |
| S9 | Android release build is signed with the debug key. | `frontend/android/app/build.gradle.kts:32` |

No hard-coded secrets, committed `.env`, or credentials were found in tracked files (`git grep` scan clean; `backend/.env` is untracked and ignored).

### Backend / API
* B1 `synchronize: true` in production: a bad entity edit can alter/drop data on boot. No migrations.
* B2 No shared exception filter, no request id, plain `console.log` / default Nest logger; unhandled errors are not correlated.
* B3 `/health` is liveness only; nothing checks the DB. Deploy smoke test hits `/recipes` instead.
* B4 Data integrity gaps: reviews/comments/favorites/meal-plan accept a `recipeId` that does not exist; a comment `parentId` may belong to another recipe; users can post unlimited reviews per recipe.
* B5 Missing indexes on `recipeId` (reviews, comments), `userId` (meal plan, folders), `uploaderId`, `createdAt` (recipes list sort).
* B6 `refreshRecipeAggregate` loads every review into memory to compute AVG/COUNT, outside a transaction; `toggleLike` is read-modify-write on a JSON column (lost updates under concurrency). `collectDescendantIds` loads every comment of the recipe.
* B7 `GET /recipes`, `/reviews`, `/comments` are unpaginated.
* B8 `viewCount` is never incremented, so "popular" sorting in the app is dead.
* B9 DTOs lack length limits (`content`, `name`, arrays), `imageUrl`s are unconstrained strings.
* B10 No lint/format tooling for the backend.

### Frontend
* F1 `RecipeProvider.init()` swallows `ApiException` → a failed load looks like "no recipes"; no error or retry state.
* F2 No global 401 handling: expired token mid-session leaves the user "logged in" with failing calls.
* F3 `baseUrl` is hard-coded to `localhost`/`10.0.2.2` — cannot target the deployed VM or a real phone without editing source.
* F4 `use_build_context_synchronously` in `profile_screen.dart` (4 places) — latent crash after `await`.
* F5 Formatting not enforced (62/70 files differ from `dart format`).
* F6 Several 400–700 line screens (`detail_screen.dart` 729, `home_screen.dart` 606). Not blocking; refactor only when touched.
* F7 Forgot-password screen depends on the insecure endpoints from S1/S3.

### CI/CD & Ops
* C1 Backend CI has no lint, format, or `npm audit`. Dockerfile is only built on `main`, so a broken Dockerfile is found after merge.
* C2 Frontend CI has no format check or compile check (`flutter build`).
* C3 No dependency update automation.
* C4 **No rollback.** Deploy pulls `:latest`; on a failed smoke test the new containers stay up and the previous image is not restarted. `docker image prune -f` removes old images.
* C5 No `HEALTHCHECK` in the Dockerfile / compose; no container restarts on a wedged process.
* C6 Grafana (3001) and backend (3000) are published on all interfaces by compose.

## 4. Technical Debt (summary)
Schema management (B1, B5), unbounded queries (B6–B7), untested modules (reviews, comments, favorites, meal plan have no dedicated tests), formatting drift (F5), large screens (F6), missing operational docs.

## 5. Security Risks (ranked)
1. S1 account takeover (critical, trivially exploitable on the public VM).
2. S2 forgeable tokens if env is misconfigured (critical, one missing variable).
3. S5 brute force / CPU DoS on bcrypt endpoints; S4 known-vulnerable libs.
4. S3, S6, S7, S8, S9.

## 6. Testing Gaps
* No e2e for favorites, folders, reviews, comments, meal plan, profile, change-password, delete-account.
* No cross-user authorization tests except recipes.
* No test for config validation (missing `JWT_SECRET`), rate limiting, error shape, readiness.
* Frontend: no test for 401 handling, error/retry state, forgot-password flow.

## 7. CI/CD Gaps
Lint, format, audit, PR-time Docker build, compile check for Flutter, dependency updates, deploy rollback, readiness-based smoke test.

## 8. Target Architecture

Keep the current layering (it is already right-sized). Add only cross-cutting pieces:

```
request ─▶ helmet · CORS allow-list · rate limit · request-id middleware
        ─▶ ValidationPipe ─▶ Guard (JWT) ─▶ Controller (thin)
        ─▶ Service (rules, ownership, transactions) ─▶ Repository ─▶ DB (migrations)
        ◀─ AllExceptionsFilter (uniform JSON error, no stack/internal details)
logs: one JSON line per request/error with requestId; never tokens/passwords
health: /health (liveness + revision) · /health/ready (DB ping)
```

Flutter: unchanged layering; `ApiClient` gains configurable base URL and an `onUnauthorized` hook; providers expose `error` + `retry`.
