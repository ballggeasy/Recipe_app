# Deployment

## Pipeline

```
push / PR ──▶ backend.yml:  lint · format · build · unit + e2e   (job: check)
                            npm audit (high/critical, shipped deps) (job: audit)
                            Docker build + smoke test, no publish   (job: image, PRs only)
          ──▶ frontend.yml: dart format · analyze · test            (job: analyze-and-test)
                            Android debug APK build                 (job: build)
          ──▶ ansible.yml:  syntax check · ansible-lint · deploy-script behaviour tests

merge to main ──▶ backend.yml publish:  build image → smoke test → push to GHCR
                                        tags: latest, sha-<commit>
                                        → signed webhook asks the VM to deploy
VM (pull-based) ──▶ recipe-deploy: pull → run sha-<commit> → wait for /health/ready
                                   → ok: record it   → not ok: roll back automatically
```

Nothing in GitHub can run code on the VM: CI only sends an HMAC-signed "please deploy" request; the VM pulls the image itself (and also polls hourly as a fallback). Setup of the VM is in [`ansible/README.md`](../ansible/README.md).

The image smoke test (`.github/scripts/smoke-image.sh`) proves two things before anything is published: the image **refuses to start without `JWT_SECRET`**, and when started the way the VM does it (production mode) it becomes ready and reports the commit it was built from.

## Configuration

Backend environment variables (`backend/.env.example`; on the VM the file is `/opt/recipe-backend/.env`, mode 0600, generated by Ansible and never overwritten):

| Variable | Required | Default | Notes |
|----------|----------|---------|-------|
| `JWT_SECRET` | **yes** | – | Server refuses to start without it. In production: ≥ 32 chars and not a placeholder. Ansible generates 64 random chars. |
| `JWT_EXPIRES_IN` | no | `7d` | Access token lifetime. |
| `PORT` | no | `3000` | |
| `DB_PATH` | no | `./data/app.sqlite` | `/app/data/app.sqlite` in Docker (volume `data`). |
| `UPLOADS_DIR` | no | `./uploads` | Served at `/uploads/` (volume `uploads` in Docker). |
| `NODE_ENV` | no | – | The Docker image sets `production`: stricter secret rule, JSON logs, no CORS headers unless configured. |
| `CORS_ORIGINS` | no | none in production, any origin otherwise | Comma-separated origins allowed for browsers (Flutter web). Native apps do not need it. |
| `TRUST_PROXY` | no | off | Number of reverse proxies in front of the app. Set it when behind one, otherwise rate limiting sees every client as the proxy's IP. |
| `RATE_LIMIT_PER_MINUTE` | no | `120` | Per client IP, per route. |
| `AUTH_RATE_LIMIT_PER_MINUTE` | no | `10` | Login, register, change/reset password. |
| `ALLOW_INSECURE_PASSWORD_RESET` | no | off | **Local development only.** See [SECURITY.md](SECURITY.md). |
| `APP_REVISION` | – | `dev` | Set by the image build (commit SHA); shown by `/health`. |
| `GRAFANA_ADMIN_PASSWORD` | yes (compose) | – | Grafana login for user `admin`. |
| `GRAFANA_PORT` / `GRAFANA_BIND` / `HOST_PORT` | no | `3001` / `0.0.0.0` / `3000` | Published ports (compose). Set `GRAFANA_BIND=127.0.0.1` to reach Grafana only through an SSH tunnel. |

Flutter app: the API address is chosen at build/run time, defaulting to `localhost:3000` (`10.0.2.2:3000` on the Android emulator):

```bash
flutter run --dart-define=API_BASE_URL=https://api.example.com
flutter build apk --release --dart-define=API_BASE_URL=https://api.example.com
```

The shipped config for the Azure VM is `frontend/config/azure.json` (HTTPS): `flutter run --dart-define-from-file=config/azure.json`. Android only allows plain HTTP to the emulator and localhost (`network_security_config.xml`), so a build pointing at an `http://` host other than those will not connect. The main Android manifest also declares the `INTERNET` permission now; it used to exist only for debug/profile builds, so a release APK could not reach any backend.

The Android **release** build is still signed with the debug key (`frontend/android/app/build.gradle.kts`). Create a keystore and a `key.properties` before publishing to a store; this cannot be done in the repo.

## HTTPS

The API is served over HTTPS by **Caddy** on the VM (Ansible role `reverse_proxy`): Caddy gets a Let's Encrypt certificate for `api_domain`, renews it by itself and proxies to the backend on `127.0.0.1:3000`. It is enabled when `api_domain` is non-empty (`ansible/group_vars/recipe_vm.yml`); leave it empty to serve plain HTTP.

What has to be true outside the repo:
- `api_domain` resolves to the VM. On Azure: Public IP -> Configuration -> *DNS name label*, which gives `<label>.<region>.cloudapp.azure.com`; the public IP must be Static.
- The network firewall allows TCP **80** (Let's Encrypt HTTP challenge and HTTP->HTTPS redirect) and **443**. Once HTTPS works, port 3000 can be closed there.

What the role changes on the VM:
- `/opt/recipe-backend/.env` gets `TRUST_PROXY=1` (the backend sees real client IPs, so rate limiting is per client instead of per proxy) and `BACKEND_BIND=127.0.0.1` (compose publishes the API on localhost only, so nobody can reach it around the proxy and forge `X-Forwarded-For`). Existing containers pick this up the next time compose recreates them (a deploy, or `docker compose up -d --force-recreate backend`).
- Caddy runs as the `caddy` systemd service; `systemctl status caddy`, `journalctl -u caddy`.

Check: `curl -sI https://<api_domain>/health` should return 200 with a certificate issued by Let's Encrypt.

## Health and monitoring

| Endpoint | Meaning |
|----------|---------|
| `GET /health` | Liveness: `{ "status": "ok", "revision": "<commit>" }` — which build is running. |
| `GET /health/ready` | Readiness: answers 200 only if the database responds, else 503. Used by the deploy script and the Docker `HEALTHCHECK` (`docker ps` shows `healthy`/`unhealthy`). |
| `GET /metrics` | Prometheus metrics (request counts/latency by route pattern, process stats). Scraped by the bundled Prometheus; Grafana dashboard is provisioned. |

Logs are one JSON object per line in production (`docker logs`), each request with `requestId`, method, path (no query string), status and duration. The same `requestId` is returned to the client in `X-Request-Id` and in error bodies, so a user's failing request can be found in the logs.

## Rolling back

The deploy script keeps state in `/opt/recipe-backend/`: `.deployed-revision` (running), `.previous-revision` (the one before), `.failed-revision` (skipped until a newer image appears), `.pinned-revision` (manual pin).

**Automatic.** If a new revision does not become ready within ~60 s, the script redeploys the previous revision, marks the bad one as failed (it is not retried every hour) and exits non-zero, so `systemctl status recipe-deploy.service` shows a failure. Look at `journalctl -u recipe-deploy -n 100`.

**Manual** (e.g. a bug that passes the health check). On the VM:

```bash
cat /opt/recipe-backend/.previous-revision                 # the revision before the current one
sudo -u recipe-deploy /usr/local/bin/recipe-deploy --revision <commit-sha>
# ...later, when a fixed build is on main:
sudo -u recipe-deploy /usr/local/bin/recipe-deploy --unpin
```

`--revision` deploys exactly that commit's image (`ghcr.io/<owner>/recipe-backend:sha-<commit>`, plus the compose/monitoring config of that commit) and pins it: automatic deploys are paused until `--unpin`, so the rollback is not undone by the next webhook. Only the running and the previous image are kept on the VM; older ones are pulled again from GHCR.

**Database caveat.** Migrations only move forward. A rollback runs old code against the *new* schema, which is safe for additive migrations (new nullable columns, indexes), which is what [DATABASE.md](DATABASE.md) asks for. Back up the volumes before deploying a revision that adds a migration.

**What has and has not been verified.** `ansible/tests/test_recipe_deploy.sh` runs the whole script (deploy, skip, rollback, failed-revision memory, pin, cleanup) against stubbed `docker`/`git`/`curl`, and CI runs it. It has not been run on the real VM or against real Docker from the repository's CI; do one rollback rehearsal on the VM after the first deploy with this version (`--revision <previous>` then `--unpin`).
